## Architecture

| ID | Decision | Reason |
|---|---|---|
| D-010 | **Modular monolith:** one app, one login, one database split into a section per module. Not microservices. | Simple, consistent data, cheap to run, can split later if ever needed. |
| D-011 | **7 modules:** M1 CRM · M2 Contracts & Renewals · M3 Projects · M4 WebCare · M5 Finance · M6 Team · M7 Academy. | Each owns a clear set of records. |
| D-012 | **Shared Core:** login and roles, price list, tasks and reminders, meetings and calendar, messaging, automation engine and builder, files, activity log, search, import/export, settings, integration doors, AI door, API and MCP. | Used by every module. |
| D-013 | **Command Centre and Reports only read**; they own no data. | Views never change data. |
| D-014 | **Floor rules:** ask only downward, announce events to reach upward, no loops. Floors: CRM + Team → WebCare + Finance → Contracts & Renewals → Projects; Academy above CRM, Team and Finance. | Keeps modules enclosed and prevents chaos. |
| D-015 | **Each module owns its data.** Others refer by ID and never copy or write it. Exception: issued invoices keep a frozen snapshot of what was printed. | One source of truth; GST invoices must not change. |
| D-016 | **Renewal split:** Contracts & Renewals owns what the client pays and when; WebCare owns vendor expiry dates and costs. | Two different facts, two owners. |
| D-017 | **Settings, not code:** roles, lead sources, pipeline stages, senders, templates, rules, languages and leave quotas are all editable settings. | Owner changes things without a developer. |
| D-018 | **Doors:** every outside service connects through one door in Core. The door standard and a **ready, documented slot for every planned integration** exist from step 3.1 (CORE-123); each door is built in its slot when its account exists, then switched on by pasting keys and pressing Test. *History:* every door built before keys were bought; revised (2026-10-01, round 16) with the owner's OK (must-have 17). | Swapping or adding tools never touches modules; no untested code for unused services. |
| D-019 | **Windows:** every action (by a person, automation, API, MCP or AI) goes through a module's window with the same permission checks and logging. | One safe path for everything. |
| D-020 | **SaaS-ready from day one:** a company ID on every record, company separation enforced centrally in Core. | Selling to other agencies later needs no redesign. |
| D-021 | Every amount stores a currency; every time is stored in UTC and shown in IST. | Future-proofing at almost no cost. |

Locked at the Release 1 Gate 3 (2 Nov 2026). | Standard, well supported, runs the same locally and on a server. |
| D-140 | **Passwords live outside Nexus, in self-hosted Vaultwarden** (free, Bitwarden-compatible, on YTP's own server). Nexus stores only references (item link, owner, last verified) and never reveals a password; clients get their logins through the vault's secure share. Vault rules: HTTPS, invite-only, 2-step login for everyone, admin page locked, daily encrypted backup off the server, monthly update and restore test. Until the server exists, a free Bitwarden cloud account can be used and imported later (C3). (2026-10-01, round 16) | A Nexus problem can never expose client accounts; the AI never sees passwords; owner's choice. |
| D-143 | **Google sign-in from Foundation (step 2.4)**, free; email and password also work. Who may sign in is an allow-list of email addresses (Gmail or company), plus a whole company domain once YTP uses Google Workspace (C8). (2026-10-01, round 16; switch added in round 25) | Fewer passwords and Google's own security; staff use mixed accounts. |
| D-146 | **Portal isolation:** the client and student portals only ever return the logged-in person's own company or student records, proven by automated tests; portal totals equal the invoice records (NFR-022, C10). (2026-10-01, round 16) | The old Agency OS client portal showed other companies' task names. |
| D-147 | **The data model for all modules' main records is locked at step 1.7**, before Phase 2 starts (C11). (2026-10-01, round 16) **Done 2 Nov 2026:** `docs/DATA-MODEL.md` v0.3, approved at the Release 1 Gate 3. | Later modules never force changes to finished ones. |
