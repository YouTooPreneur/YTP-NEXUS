**Chain:** step 2.4 (sign-in and people) · **Release:** 1 · **Module:** Core · **Part:** Backend · **Depends on:** TASK-0015, TASK-0018, TASK-0019, TASK-0023, TASK-0084 (all Done) · **Lane:** careful (sign-in) · **Card style:** fast (D-202): the rules, exact SQL, exact lines and the planner's tests are given; you write the code

**Builder:** Claude (a building session, D-202) · **Reviewer:** Claude (planning session)

**Goal:** people can **sign in**. Better Auth (pinned `1.7.14`) runs at `/api/auth` with its own tables in the `auth` schema: email and password sign-in, Google sign-in (the start and its return address), sign-out, the current session, and password reset links. Only people the Owner added can sign in (self sign-up is off): `createSigninUser` adds one (an invited person of one company, with an optional password, used later by the people cards and the first-start command); the first good sign-in makes them active, and a disabled person is refused. Every sign-in leaves `signin_ok` or `signin_failed` (with a fixed reason) in the security log, in the person's company chain, or in the system chain when the email is unknown. Only the seven agreed sign-in doors are open; every other Better Auth door answers 404, the reset link's own GET door included, because the reset email links to the reset screen at `APP_URL` instead. Nothing secret (a password, a session token, a reset token, Google's tokens) ever reaches the log.

## RULES FOR THE CODE YOU WRITE
1. **Package:** `pnpm --filter @ytp/api add better-auth@1.7.14 --save-exact`. No other new package.
2. **Tables** (`src/db/auth-schema.ts`, `pgSchema('auth')`): Better Auth 1.7.14's `user`, `session`, `account` and `verification` tables with the columns its Drizzle adapter needs for the features used here, every `id` a `uuid` with the default `core.uuid_v7()` (Better Auth leaves the ID to the database: set it so, for example `advanced.database.generateId: false`; check it against 1.7.14) and every link to `user` a `uuid`. The user also has Nexus's fields: `company_id` uuid, required, linked to `core.companies` with `onDelete: 'restrict'`; `status`, the enum `auth.user_status` (`invited`, `active`, `disabled`), required, default `invited`; `failed_signins` smallint, required, default 0; `locked_until` timestamptz. These fields are Better Auth `additionalFields` with `input: false`, so no request can set them. The email is unique and stored in lower case. `drizzle.config.ts`'s schema line becomes exactly `  schema: ['./src/modules/*/schema/*.ts', './src/db/auth-schema.ts'],`.
3. **Database:** Better Auth's adapter uses a Drizzle database on the existing request pool, from one new named export of `database.ts` (for example `authDatabase()`), added directly before the comment line that starts `// Step 5: runs the rest of a request`; never a new pool. Nothing reads a setting or connects when a file is loaded.
4. **The auth instance** (`signin/auth.ts`): `getAuth()` makes it on first use (never when the file is loaded) from `APP_URL` (its origin is the `baseURL`, with `basePath: '/api/auth'`, and the only `trustedOrigins` entry), `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`; `emailAndPassword` enabled with `disableSignUp: true` and `sendResetPassword` handing the person's email and `resetLink(token)` to the reset mailer; Google with sign-up off (only added people); `rateLimit: { enabled: false }`, no cookie cache, `telemetry: { enabled: false }`; its `logger` is `authLog(logger)`. `authHandler()` returns an Express handler that calls Better Auth's `toNodeHandler(getAuth())` on first use, so `createApp` still works with no settings. `authLog(logger)` returns `(level, message, ...args) => logger[<pino level>]({ err: args.find((a) => a instanceof Error) }, message)` (Better Auth's `success` writes at info): only the message and a cleaned error, never the other arguments.
5. **Who may sign in** (Better Auth hooks): a person with status `disabled`, or with no company, is refused and gets no session; the first good sign-in of an `invited` person makes them `active`. Every email sign-in attempt writes one security entry with `writeSecurity` inside a security write: `signin_ok` (the person's ID) or `signin_failed` with `details: { reason }`, the reason one of `unknown email`, `wrong password`, `disabled`, in the person's company chain (`securityWrite(companyId, ...)`), or in the system chain for an unknown email (`securityWriteWithoutCompany`, no user ID). Never an error's message in `details`.
6. **People** (`signin/users.ts`): `createSigninUser({ companyId, email, name, password? })` adds an invited person (email in lower case) and, when a password is given, its `credential` account with the password scrambled by Better Auth's own hasher; it gives back the person's ID; a second person with the same email is refused.
7. **The reset email** (`signin/reset-email.ts`): `resetLink(token)` is exactly `` `${origin of APP_URL}/reset-password?token=${encodeURIComponent(token)}` ``; `setResetMailer(send)` sets the function that sends `{ to, link }` (tests set it). Until the email door exists (TASK-0029 wires it), the default mailer logs `logger.warn({ userId }, 'reset email not sent: the email door comes with TASK-0029')`, never the link or token.
8. **Open doors only:** `signin/open-routes.ts` exports `OPEN_AUTH_ROUTES`, exactly the seven strings of `tools/verify/auth-routes.json` (`'POST /api/auth/sign-in/email'` and so on), and imports nothing. `signin/auth-routes.ts` exports `openAuthRoutesOnly()`, a middleware that answers 404 `not_found` (through `AppError`, Nexus's own error format) for every method and path under `/api/auth` that is not on that list. `scripts/list-routes.ts` imports `OPEN_AUTH_ROUTES` and prints `authRoutes: [...OPEN_AUTH_ROUTES],`.
9. **Logging:** `SECRET_KEYS` in `shared/logging.ts` (one line) also has `'accessToken'`, `'refreshToken'` and `'idToken'`.
