# TASK-0030 · Roles, permission list and default grants

**Chain:** step 2.4 (sign-in and people), first card · **Release:** 1 · **Module:** Core · **Part:** Backend (no door) · **Depends on:** TASK-0017 (Done) · **Lane:** careful (who may do what) · **Card style:** fast (D-202): the exact SQL and module-card lines are given; you write the schema and service code to the rules below and the tests

**Builder:** Antigravity or Codex, whichever is free first (D-202) · **Reviewer:** Claude (planning session)

**Goal:** the data behind "who may do what". Five tables: **roles** (each company's roles; nine are made by default: Owner, LLP partner, Manager, HR, Accounts, Staff, Trainer, Client contact, Student, each with its two-step rule, sign-out time and phone menu), **role permissions** (which action each role may do, with a scope own, team or all), **hidden fields** (which fields a role does not see), the **permission list** (every action a module offers, registered from code on every start, so new permissions appear without code) and **default grants applied** (so each module's starting grants are given once and never undo the Owner's changes). Three functions in `service/roles.ts`: `registerPermissions`, `makeDefaultRoles` and `applyDefaultGrants`. A grant or hidden field can only point at a role of the same company: the link includes the company, and the shared catalogue check now refuses any link between company tables that does not. No door or screen yet (the role builder is TASK-0044; the permission check is TASK-0031; the first-start command TASK-0047 calls these functions).

## RULES FOR THE CODE YOU WRITE
- **Schema** (`schema/roles.ts`, with `core` from `./schemas.js`, `companies` from `./companies.js`): the columns, types, defaults, keys and links are exactly those `apps/api/test/db/roles.test.ts` checks (read its first describe block): `core.roles` (its own `id` from `core.uuid_v7()`, `UNIQUE (company_id, key)` and `UNIQUE (company_id, id)`), `core.role_permissions` (its own `id`, `scope` of the enum `core.permission_scope` own/team/all, `UNIQUE (company_id, role_id, module, action)`), `core.role_hidden_fields` (key of four columns), `core.permission_catalogue` (key `module` + `action`, no company: a system table), `core.default_grants_applied` (key of three columns). Every `company_id` is required and linked to `core.companies` with `onDelete: 'restrict'`; grants and hidden fields link to the role with drizzle's `foreignKey({ columns: [table.companyId, table.roleId], foreignColumns: [roles.companyId, roles.id] })`, restrict on delete. Export the tables as `roles`, `rolePermissions`, `roleHiddenFields`, `permissionCatalogue`, `defaultGrantsApplied` and the enum as `permissionScope`.
- **Service** (`service/roles.ts`): works only in the transaction on the request context (`getContext().tx`; refuse with `the roles need the transaction`) and the context's company; every query on a company table filters with `forCompany`; it opens no transaction and imports no pools. It exports:
  - `PermissionEntry` (`module`, `action`, `label`, `hideableFields?`, `defaultGrants?` keyed by role key with `{ scope, hidden? }`, `grantsVersion`, `release`) and `CORE_PERMISSIONS`: the 27 Release 1 permissions of DATA-MODEL 3.2 (each with a short English label, `grantsVersion: 1`, `release: 1`, `defaultGrants: { owner: { scope: 'all' } }`, and for `core.record_history` `view` also `manager: { scope: 'all' }`).
  - `DEFAULT_ROLES` and `makeDefaultRoles()`: the nine roles with exactly the keys, names, two-step, minutes and phone menus the test lists (`is_default` true), made in the context's company only when a role with that key is missing; each new role is logged with `writeActivity` (`recordType: 'role'`, `action: 'created'`, `actor: { type: 'system', label: 'default roles' }`); it gives back `{ [key]: id }` for all nine.
  - `registerPermissions(entries)`: adds each entry to the catalogue, or updates its label, hideable fields, default grants, grants version and release when it exists.
  - `applyDefaultGrants()`: for each catalogue entry whose version this company has not received yet (no `default_grants_applied` row, or a lower version): for each role key in its default grants that exists in the company, add the grant (nothing when it already exists) and its hidden fields, then record the version; it gives back how many grants it added. A grant the Owner removed comes back only when the module raises the version.
