# Core module card

**Floor:** ground · **Owns the schema:** `core` (and `audit`) · **First release:** 1

Every module is built from the same 6 parts (TECH-DESIGN section 2). If it is not on this card, the module does not do it. The verify command's module-card check reads this file: every API door's `operationId` must be listed under **Window**, and every announcement under **Announcements**, each as a list item that starts with the name in backticks. From TASK-0089 the reverse is checked too: every such item must be a door or announcement this module already has, so each line is added by the card that builds that door or announcement, never in advance. Entries start with `- ` at the start of the line; other bullet styles are not read.

## Data
- `core.companies`: one company using Nexus; a system table with no company row rule, read-only for the app (DATA-MODEL 3.1)
- `auth.user`, `auth.session`, `auth.account`, `auth.verification`: Better Auth's sign-in tables (people who may sign in, with Nexus's company, status, failed sign-ins and lock; sessions; Google and password accounts; reset links); system tables with no row rule, touched only by `modules/core/signin/`, `modules/core/users/` and `src/db/` (DATA-MODEL 3.2, CORE-001)
- `audit.activity_log`: one entry per change or automatic action (who, what, when, old and new values); a company table the app may only add to and read (DATA-MODEL 3.3, CORE-090)
- `core.idempotency_keys`: the first answer to a request that changes data, kept 24 hours under the screen's double-click key; a company table the app may read, add and update (DATA-MODEL 3.4, NFR-021)
- `core.roles`: a company's roles, nine made by default (`makeDefaultRoles`), each with its two-step, sign-out time and phone menu; a company table the app may read, add and change, never delete (DATA-MODEL 3.2, USR-002, USR-006)
- `core.role_permissions` and `core.role_hidden_fields`: what each role may do, with its scope, and which fields it does not see; company tables linked to the role of the same company (USR-002)
- `core.permission_catalogue`: every action a module offers, registered from code on every start (`registerPermissions`); a system table the app may read, add and change (USR-003)
- `core.default_grants_applied`: which module defaults a company has already received, so each version is given once (USR-006)
- `core.users`: everyone who can sign in, one row per person under the same ID as their sign-in record (no database link to it), with their company, name, one role (linked to the role of the same company), sign-in methods (Google, a password or both) and manager; a company table the app may read, add and change, never delete: people are never removed (DATA-MODEL 3.2, USR-001)
- `core.user_preferences`: each person's language, colour, time zone, time and date format and daily summary time, keyed by company and person, India's time and 12-hour times by default; a company table the app may read, add and change, never delete (CORE-112)
- `core.settings`: the values a company changed for its settings, each with its version; a company table the app may read, add and change (DATA-MODEL 3.1, CORE-012)
- `audit.security_log`: one entry per security event, in one chain of fingerprints per company plus the system chain (no company); added only through `audit.add_security_entry`, never changed or deleted (DATA-MODEL 3.3, CORE-092)
- `core.error_events`: recent server errors for Monitoring, under the company of the request or job that met them or with no company (a system error); added only through `core.record_error`, with the cleaned message only; the app reads its own company's (DATA-MODEL 3.4, CORE-140)
- `core.rate_counters`: the request counters of the limits, one row per bucket (for example `signin:ip:<address>`) and fixed window, refused requests included; a system table with no company that the app may read, add and change (DATA-MODEL 3.4, NFR-020)
- `core.outbox`: the announcements a save posts, each kept until the worker has delivered it to every listener, with the delivery's attempts, last error and next try; a company table the app may read and add to, changing only those delivery columns (DATA-MODEL 3.3, NFR-003)
- `core.event_receipts`: which listener has handled which announcement, so none handles one twice; a system table the app may read and add to (DATA-MODEL 3.3, NFR-003)

## Rules
- A table's own `id` key is a time-ordered ID (UUID version 7) made by the database function `core.uuid_v7()`, Better Auth's tables included; a key that is another table's ID, a key of several columns and `audit.security_log`'s chain number keep the form DATA-MODEL section 3 gives them, and drizzle's and pg-boss's own tables keep their tools' keys (DATA-MODEL section 2)
- Every company table gets the company row rule in its own database change, `CALL core.add_company_rules('<schema.table>');`, and every query on it runs inside `withCompany` and filters with `forCompany` (`src/db/company.ts`; TECH-DESIGN 5.1, CORE-014)
- Rows with no company (the security log's system chain, later the errors before a company is known) are written and read only through `nexus_system`'s database functions, never with `withCompany`; every security event is written with `writeSecurity` (`modules/core/repository/security-log.ts`), and within one request every security write that writes an entry runs before any entry the request's own transaction writes (TECH-DESIGN 5.1, CORE-092)
- Every server error (an unexpected error, or an `AppError` of 500 or more) is kept for Monitoring by the error handler with `recordError` (`modules/core/repository/error-events.ts`), without making the answer wait, under the request's company or as a system error with none; any column that keeps an error's text outside the log holds only `safeErrorMessage(error)` (`src/shared/logging.ts`); rows with no company are read only through `core.system_errors` and `core.system_security_entries`, which refuse once Nexus has a second company, and only the platform operator's doors call them (while Nexus has one company, its Owner; TECH-DESIGN 5.1 and section 7, CORE-140)
- The sign-in doors (`/api/auth`) and the two-step doors (`/api/core/two-step`) are under the per-address limit (`src/shared/address-limit.ts`), mounted in `app.ts` right after the same-site check and before the body is read: every request from one address is counted with `hitLimit` (`modules/core/repository/rate-counters.ts`) in the `signin` bucket, refused ones included; past the limit the answer is 429 `too_many_requests` with `Retry-After`, and the first refused request of a window writes one `limit_hit` entry in the security log's system chain; the values come from `ADDRESS_LIMITS` in the environment file (TECH-DESIGN section 2 step 2, NFR-020)
- Sign-in runs through Better Auth (`modules/core/signin/auth.ts`, pinned 1.7.14) at `/api/auth`, after the per-address limit: only the seven doors of `modules/core/signin/open-routes.ts` (the list in `tools/verify/auth-routes.json`) are open and every other `/api/auth/` door answers 404; self sign-up, Better Auth's own limiter, cookie cache and telemetry are off; only people added with `createSigninUser` and not disabled may sign in; every sign-in writes `signin_ok` or `signin_failed` (a fixed reason, in the system chain when the email is unknown); the reset email links to the reset screen at `APP_URL`, never to a sign-in door; Better Auth's own errors keep its `{ code, message }` shape, the one exception to TECH-DESIGN 6.7 (TECH-DESIGN 6.1, CORE-001)
- Every save writes its activity-log entry with `writeActivity` (`modules/core/repository/activity-log.ts`) in the save's own transaction, after the work and before any announcement; `changes` holds only the changed fields as `{ field: { old, new } }`, named as in the record's API contract (a new record: `old` is null; a delete or restore: `{}`), and never a password, code, token or key; a change to a record with no ID of its own (a setting, a switch) is logged against the record that holds it, for a company's settings the company (TECH-DESIGN section 2 step 13, CORE-090)
- Every announcement is posted with `announce` (`modules/core/repository/outbox.ts`) in the save's own transaction, after its activity-log entry, never inside a security write (whose transaction stays when the save is undone): its event is registered in `allAnnouncements` (`src/announcements.ts`) and listed on its module card under `## Announcements`, it has a version, and its payload holds IDs and the facts needed, never a copy of another module's record and never a secret; the worker delivers it later, once to each listener (D-014, NFR-003)
- Announcements are delivered by the worker with `deliverPending` (`modules/core/events/delivery.ts`), company by company, each in a context of its own and one transaction with its company set (`inCompanyTransaction`, `src/db/database.ts`): every listener has a permanent `name`, its event and the versions it reads, and runs in a savepoint of its own after its receipt is added, so it handles an announcement at most once and what it writes is kept only with its receipt; the announcement is marked delivered once every listener has its receipt, and otherwise tried again after 1, 5, 15 and 60 minutes, at most 5 times, each failure logged and kept with `recordError` under its company (D-014, NFR-003)
- Background jobs run through pg-boss (pinned 12.38.0) in the worker only: each job is defined with `defineJob` (`src/jobs/jobs.ts`), sent with `sendJob` with the company of the request, and run once by `startJobs` in a fresh background context and a transaction of that company (`inCompanyTransaction`); a failure is logged as `job failed` with its ID, kept with `recordError(error, 'worker')`, and handed back to pg-boss as its cleaned message only; the `pgboss` schema and every queue are made by database changes as `nexus_owner` (`queueSql`), never by the app (NFR-003, TECH-DESIGN 5.2)
- Every request that changes data carries an `Idempotency-Key` (a UUID the screen makes, one per change, sent again on a retry); a repeat within 24 hours by the same person to the same door gets the first answer without running again (`src/shared/idempotency.ts`, TECH-DESIGN section 2 step 12, NFR-021)
- Each setting is defined once in code with `defineSetting` (`modules/core/service/settings.ts`) by the card that first uses it, with a `<group>.<name>` key, its rule, default and help, and is listed on its module card under `## Rules` in a line that starts with `Setting` and gives its key, what it controls and its default; only changed values are stored in `core.settings`; every save checks the value and the version it was based on (409 `stale_version` when someone saved first) and is written to the activity log in the same transaction; a setting never holds a secret (CORE-012, TECH-DESIGN 6.6)
- Permissions are registered with `registerPermissions` (`modules/core/service/roles.ts`), and each module's default grants are given with `applyDefaultGrants` once per version, never undoing the Owner's changes; a link between two company tables always includes `company_id` on both sides (for example `FOREIGN KEY (company_id, role_id) REFERENCES core.roles (company_id, id)`), and the catalogue check refuses one that does not (TECH-DESIGN 5.1, USR-002, USR-003, USR-006)
- Every non-public door first learns who is asking with `whoIsAsking` (`modules/core/signin/session.ts`), before its transaction opens: it asks Better Auth for the session without refreshing it (only the open sign-in doors refresh a session) and puts the person's ID, their company and the session's ID on the request's own context, never the session token; no session, a tampered or ended one, or a person who is not active answers 401 `not_signed_in` (TECH-DESIGN section 2, step 4; CORE-006)
- Core serves everyone and asks no module (D-014)
- Core's sign-in code lives in `modules/core/signin/` and its users code in `modules/core/users/`; only these two folders and `src/db/` may touch the `auth` schema (the auth-schema wall, TECH-DESIGN 5.1)
- Personal values are removed from the activity log only by `erasePersonalValues` (`modules/core/repository/erasure.ts`), called by the Owner's deletion-request action in the request's own transaction: every entry of the record, in that company only, keeps its fields but its label and the named fields' old and new values become `[removed on request]` (`core.erase_personal_values`, the only way the system account may change an entry), and a `data_erased` security entry is written last; stored double-click answers are not changed (they expire within 24 hours) (DPDP, NFR-010)
